# Nexora

A plugin-based personal AI assistant for the desktop. Users connect
**extensions** (Excel, Word, MCP servers, ...) the same way they would add
connectors. Each extension runs isolated and can be added or removed at any
time. The AI drives them through **Code Mode**: instead of calling tools one at
a time, it writes a short script against a typed `tools` API:

```js
const rows = await tools.excel.readSheet({ path: "/home/me/q3.xlsx" })
await tools.word.createDocument({
  path: "/home/me/q3-summary.docx",
  title: "Q3 summary",
  blocks: rows.slice(1).map(([region, total]) => ({ text: `${region}: ${total}` })),
})
return rows.length
```

## Installing

Download the installer for your system from the
[latest release](https://github.com/Diwanshumidha/nexora/releases/latest):
a `setup.exe` for Windows, a `.dmg` for macOS, or an AppImage / `.deb` for
Linux. The first-run setup downloads the Node.js runtime extensions need,
so nothing else has to be installed.

Builds are not yet signed with a paid certificate, so the first launch
shows a warning:

- **Windows:** "Windows protected your PC" → **More info** → **Run anyway**.
- **macOS:** open Nexora once, then **System Settings → Privacy & Security
  → Open Anyway**. Or run `xattr -dr com.apple.quarantine /Applications/nexora.app`.

Every release file carries build provenance, so you can check it came from
this repository's release workflow:
`gh attestation verify <file> --repo Diwanshumidha/nexora`.

## Stack

| Layer      | Tech                                                       |
| ---------- | ---------------------------------------------------------- |
| Core       | Go + [Wails v3](https://v3.wails.io)                       |
| UI         | React + TypeScript + Vite (`frontend/`)                    |
| Extensions | TypeScript on Node.js, one sandboxed process each          |
| Code Mode  | Embedded JS sandbox ([goja](https://github.com/dop251/goja)) |

## Layout

```
main.go                      Wails entry point: wires config, manager, services
internal/
  config/                    On-disk paths (~/.config/nexora), env overrides
  protocol/                  Host <-> extension JSON-RPC wire types
  extension/                 Manifest, process supervisor, manager (install/remove/route)
  codemode/                  JS sandbox runtime + TypeScript API generator
  jobs/                      Bounded FIFO job queue + worker pool
  runner/                    Runs code-mode scripts through the queue (shared by UI and MCP)
  mcp/                       MCP server over streamable HTTP (run_code / get_job)
  network/                   Built-in network providers that expose the MCP endpoint
    tailscale/               Tailscale Funnel / tailnet via tailscaled's LocalAPI (in-process)
    cloudflare/              cloudflared quick tunnel
  history/                   Persistent record of every run (history.jsonl)
  cache/                     tools.store: Code Mode's expiring key-value cache (cache.json)
  registry/                  Extension catalog client: download, verify, unpack
  permissions/               Trust modes, per-tool overrides, approval gate
  services/                  Thin Wails services bound to the frontend
frontend/                    Desktop UI: the orbit view and the Code mode page
  src/orbit/                 Orbit map, node inspector, icons
  bindings/                  Generated by `wails3 generate bindings`
build/                       Wails platform build assets and Taskfiles
docs/                        Architecture guide
```

## Getting started

Prerequisites: Go 1.26+, Node.js 22+, pnpm, and the `wails3` CLI
(`go install github.com/wailsapp/wails/v3/cmd/wails3@v3.1.0`).

Extensions, their SDK and the catalog build live in a separate repo,
[nexora-extensions](https://github.com/Diwanshumidha/nexora-extensions). Clone it next to this one:

```
projects/
  nexora/              this repo (the app)
  nexora-extensions/   SDK + extensions
```

```sh
pnpm install
wails3 task build:extensions   # pnpm build in ../nexora-extensions
wails3 task dev                # run the app with hot reload, loading those extensions
wails3 task test               # Go tests, including extension end-to-end tests
wails3 build                   # production binary in bin/
```

`NEXORA_EXTENSIONS_REPO` points the tasks and tests at a checkout elsewhere.

The `Makefile` wraps these with shorter names (`make` lists them): `make dev`,
`make test`, `make build`, `make check` (gofmt, vet, typecheck and Go tests),
and `make preview`, which runs the app in your browser (server mode) with a
throwaway profile in `.preview/`, so your real data is untouched.

### Node.js for extensions

Users don't need Node.js installed. Like VS Code, Nexora runs extensions on a
Node.js it manages: the first-run setup screen offers a one-time download of
a pinned LTS release (`noderuntime.Version`, about 60 MB from nodejs.org),
verified against checksums built into the app and kept in
`~/.config/nexora/runtime/`. Lookup order: `NEXORA_NODE`, then the managed
runtime, then `node` on PATH if it is 22.13 or newer (extensions run under the
`--permission` model, which older versions reject). Without a usable Node,
JS extensions wait with a clear error and start by themselves once the
download finishes. The managed runtime's `bin` folder is also put first on
the PATH of local MCP servers, so `npx`-based servers work too.

**Linux note:** Wails v3 targets GTK4/WebKitGTK 6.0 by default. On systems
that only have WebKitGTK 4.1 (`webkit2gtk-4.1`), build with the `gtk3` tag:
`EXTRA_TAGS=gtk3 wails3 task dev`. Use `go build -tags gtk3` / `go test -tags gtk3` for plain Go commands.

### Environment variables

| Variable                | Purpose                                                   |
| ----------------------- | --------------------------------------------------------- |
| `NEXORA_DEV_EXTENSIONS` | Extra folders (`:`-separated) scanned for extensions      |
| `NEXORA_REGISTRY_URL`   | Extension catalog (`index.json`) the **+** panel installs from |
| `NEXORA_NODE`           | Force the Node.js binary used to run extensions (default: the managed runtime, else `node` on PATH if 22.13+) |
| `NEXORA_UPDATE_URL`     | Release API checked for updates (default: this repo's latest GitHub release; `off` disables) |
| `NEXORA_NODE_MIRROR`    | Where the managed Node.js is downloaded from (default `https://nodejs.org/dist`; checksums still apply) |
| `NEXORA_WORKERS`        | Code-mode jobs executed concurrently (default `4`)        |
| `NEXORA_MAX_QUEUED`     | Jobs allowed to wait for a worker (default `100`)         |
| `NEXORA_JOB_TIMEOUT`    | Max runtime of one job (default `15m`)                    |
| `NEXORA_MCP_ADDR`       | MCP endpoint address (default `127.0.0.1:7377`, `off` disables) |
| `NEXORA_MCP_INLINE_WAIT`| How long an MCP call waits before returning a job ID (default `80s`) |
| `NEXORA_APPROVAL_TIMEOUT`| How long a tool call waits for your approval (default `5m`) |

## Connecting ChatGPT / Claude (MCP)

Nexora serves an MCP endpoint (streamable HTTP) with four tools: `get_api`,
`run_code`, `get_job` and `cancel_job`. The URL including its secret token is
shown on the **Connect AI** page (the token lives in `~/.config/nexora/mcp-token`).

The endpoint listens on localhost. Hosted AIs such as ChatGPT run in the
cloud, so they need a public URL. Pick one built-in network provider on
**Connect AI** (only one is live at a time):

| Provider   | How                                             | URL                                           |
| ---------- | ----------------------------------------------- | --------------------------------------------- |
| Tailscale  | `funnel` (public) or `tailnet` (your devices)   | `https://<machine>.<tailnet>.ts.net[:<port>]/nexora/<token>` |
| Cloudflare | `cloudflared` quick tunnel                      | `https://<random>.trycloudflare.com/mcp/<token>` |

The Tailscale port is the provider's *Port* setting (8443 by default; Funnel
also allows 443 and 10000). On 443 the URL has no port at all, e.g.
`https://laptop.tail1234.ts.net/nexora`. The exact URL is always shown on the
provider's panel, so copy it from there.

A tailnet `100.x` address is not reachable from ChatGPT's servers, so use
Funnel mode for hosted AIs. The Tailscale provider talks to `tailscaled`
directly (no CLI) and only mounts its own path. It refuses to funnel a port
that already serves your other, private services. If `tailscaled` denies
access, allow your user once with `sudo tailscale set --operator=$USER`.

### Signing in with OAuth

Clients that support MCP's OAuth sign-in (claude.ai and ChatGPT connectors,
Claude Code, Cursor, ...) don't need the token. Give them the URL without it:

| Where          | URL                                               |
| -------------- | ------------------------------------------------- |
| This machine   | `http://127.0.0.1:7377/mcp`                       |
| Tailscale      | `https://<machine>.<tailnet>.ts.net[:<port>]/nexora` |
| Cloudflare     | `https://<random>.trycloudflare.com/mcp`          |

For example `claude mcp add --transport http nexora http://127.0.0.1:7377/mcp`,
or *Add custom connector* on claude.ai with the public URL. The client
registers itself and opens a browser page showing a short code; Nexora pops
up an approval window with the same code. Approve it only if the codes match.
Approved clients are listed under *Signed-in apps* in the core panel, where
they can be signed out. Access tokens last an hour and are refreshed
automatically; a connection unused for 30 days has to sign in again. Only
token hashes are stored (`~/.config/nexora/mcp-oauth.json`).

`run_code` returns the result in the same call if the script finishes within
`NEXORA_MCP_INLINE_WAIT`. Otherwise it returns a `jobId`, and the AI calls
`get_job` (which itself waits up to the same limit) until the job is done. No
single request outlives a proxy's 100 s timeout.

## Running in the background

Nexora behaves like Discord: one process per user, one main window.

- **Closing the window hides it.** The MCP endpoint, extensions, network
  provider and approvals keep working, so a connected AI can still reach you.
- **Tray icon:** click it (or choose *Open Nexora*) to bring the window back;
  *Quit Nexora* really exits.
- **Launching it again** shows the running instance's window instead of
  starting a second copy.
- `nexora --background` starts without a window (for launching at login).
- `nexora --quit` stops the running instance, e.g. on desktops without a tray.
- **Start at login** (offered in the first-run setup, switchable in the core
  panel) registers `nexora --background` for the current user: an XDG
  autostart entry on Linux, a LaunchAgent on macOS, a `Run` key on Windows.
- **Updates:** Nexora checks the latest GitHub release shortly after launch
  and every 12 hours, and shows a banner when a newer version is out (it
  never installs anything itself). `NEXORA_UPDATE_URL=off` turns this off.

## Releasing

The version lives in `internal/version` and the packaging files;
`scripts/set-version.sh 0.2.0` updates all of them. To release, push a tag:

```sh
git tag v0.2.0 && git push origin v0.2.0
```

`.github/workflows/release.yml` stamps the tag's version into the build,
builds an AppImage and a `.deb` (Linux), a universal `.dmg` (macOS) and a
per-user NSIS installer (Windows), and attaches them with `SHA256SUMS.txt` to
a **draft** release. Publish the draft to make the in-app update check offer
it. *Run workflow* on the Release action builds a version without releasing.

Signing switches on when these repository secrets exist (otherwise builds
are unsigned: macOS Gatekeeper blocks them and Windows SmartScreen warns):

| Platform | Secrets |
| -------- | ------- |
| macOS    | `APPLE_CERTIFICATE` (base64 `.p12` of a *Developer ID Application* certificate), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`; for notarization also `APPLE_ID`, `APPLE_APP_PASSWORD` (app-specific password), `APPLE_TEAM_ID` |
| Windows  | `WINDOWS_CERTIFICATE` (base64 `.pfx` code-signing certificate), `WINDOWS_CERTIFICATE_PASSWORD` |

`.github/workflows/ci.yml` runs gofmt, vet, the Go tests and the frontend
typecheck and build on every push to `main` and every pull request.

## Extensions

Click **+** in the orbit to browse the extension catalog: install, update
(settings, data and permissions are kept) or open each one. The catalog is the
`index.json` of a nexora-extensions release (`NEXORA_REGISTRY_URL`); every
download is checked against its SHA-256 and size, unpacked with zip-slip and
size limits, and its manifest must match the catalog entry. Extensions
declare the protocol they speak; one built for a newer Nexora is refused with
a clear message instead of failing at runtime.

The last catalog fetched is saved (`catalog.json`), so the panel opens
instantly and still lists extensions offline. Nexora re-checks it in the
background every few hours; installed extensions with a newer version get an
**Update** notice, a count on the **+** node, and an **Update all** button.
You can also install a package file (`.nxext`, or the catalog's `.zip`),
which updates the extension if it is already installed (never downgrades),
or any built extension from a folder.

The first-party extensions (Files, Web, Notes, PDF, CSV, Archive, Images,
System, Excel, Word) and how to write your own are documented in the
nexora-extensions repo.

### Keeping data between runs: `tools.store`

Every script also gets `tools.store`, a built-in cache for JSON values that
outlives a single run, e.g. to remember what a previous run already processed:

```js
const seen = (await tools.store.get({ key: "inbox:last-id" })) ?? 0
// ...
await tools.store.set({ key: "inbox:last-id", value: newest, ttl: "7d" })
```

It is a cache, not a database, so it cleans itself up:

- every entry expires: 1 day by default, `ttl` up to 30 days (seconds, or
  `"30m"`, `"12h"`, `"7d"`);
- it holds at most 16 MB and 10,000 keys (1 MB per value); when a write
  would exceed that, expired entries go first, then the least recently used;
- expired entries are swept every minute and dropped on load, so they don't
  linger on disk (`cache.json`, readable only by you).

`get`, `set`, `has`, `delete`, `keys({ prefix })` and `clear({ prefix })` are
available. Store calls need no approval: it is Nexora's own scratch space.
**Code mode → Storage** shows what is stored and lets you delete entries.
Extensions can't use the `store` namespace.

### MCP servers

Any MCP server can be added as an extension: **+** → *Add an MCP server*.
Give it a name and either the command that starts it (for example
`npx -y @modelcontextprotocol/server-github`) or the URL of a remote server
(streamable HTTP). Environment variables and headers you enter become the
extension's settings, with tokens stored as secrets. Its tools then appear
under `tools.<name>` with the same trust modes and approvals as any other
extension.

Remote servers that use OAuth (most hosted ones) need no token at all: leave
the headers empty and press **Sign in** on the server's panel. Nexora
registers itself with the server, sends you through its sign-in in your
browser, and keeps the token (refreshed automatically) in its private
settings store. It never opens the browser on its own; if a sign-in expires,
the panel asks you to sign in again.

Local MCP servers are ordinary programs, so unlike Node extensions they are
**not sandboxed**: they run with your user's access. They only get a minimal
environment, never your shell's secrets. Only add servers you trust. See
[MCP-server extensions](docs/architecture.md#mcp-server-extensions) for the
manifest format.

With the default *Ask first* mode, read tools run straight away and write
tools wait for your approval in the ask window.

## The orbit

The home screen is an orrery. The **core** (the AI's way in) sits in the
middle. Around it are the **network** providers (the live one glows and links
to the core), then the **extensions**, with rings added as needed, and on the
outer ring the **history** of runs from you and from AIs, drifting slowly.
Clicking any node opens its settings in the inspector:

- **Core:** MCP URLs (local and public), queue stats.
- **Network provider:** settings, make live or turn off, public MCP URL.
- **Extension:** tools, permissions, recent use, restart or remove.
- **Run:** trace of the tools it called (drawn on the map), result, console,
  script, run again or cancel.

The **History** tab in the sidebar lists every run with search and filters
(status, AI or you). Selecting one shows its full context: a timeline of each
tool call with its arguments, duration and outcome, any approval you gave or
refused (and how long it took), the error, result, console output and the
script, with copy and run-again actions.

History is kept in `~/.config/nexora/history.jsonl` (mode 0600, last 500
runs). It can contain data your extensions read, so it never leaves the
machine.

## Security

- **Ask window.** When a tool call needs approval, a small separate window
  opens with the tool, its arguments and the script asking. It's created
  fresh, so on Linux it appears on your current workspace (and floats on
  tiling WMs, being fixed-size). On Windows and macOS it opens always on top.
  Allow buttons unlock after 1.2 s so a stray click or keystroke can't
  approve. Deny has focus, Esc denies, and there is no shortcut to allow.
  Approvals are never possible from a notification.
- **Answers:** allow once, allow for this run (until the script ends),
  always allow, deny, always block.
- **Strict mode** (core panel): every tool call asks, even read-only and
  trusted ones.
- **MCP endpoint:** requests from web pages (any `Origin` header) are refused,
  which blocks DNS rebinding and drive-by pages. Allow specific origins with
  `NEXORA_MCP_ALLOWED_ORIGINS`. Wrong tokens are throttled (valid ones never
  are), refused requests are shown in the core panel, and the token can be
  rotated there, which invalidates every old URL immediately. OAuth sign-ins
  must be approved in the app and can be signed out there; rotating the
  token does not sign them out.

## Extension settings

Extensions declare settings in `nexora.json` (text, number, toggle, choice,
secret, folder, folder list). They appear on the extension's panel. Folder
settings can **grant** read or read+edit access: Excel's *Trusted folders*
and Word's *Save folder* are the only places those extensions can touch, and
the Node sandbox enforces it. Values live in
`~/.config/nexora/extension-settings/<id>.json` (mode 0600).

## Permissions

Every tool call from a script goes through a permission gate
(`internal/permissions`). Each extension has a trust level, shown by its
ring colour on the orbit:

| Mode          | Read-only tools | Other tools                 |
| ------------- | --------------- | --------------------------- |
| Trusted       | run             | run                         |
| Ask first *   | run             | wait for your approval      |
| Read only     | run             | blocked                     |

\* default for every new extension

Any tool can override its mode (**Always allow**, **Always ask**, **Block**)
from the extension's inspector. When a call needs approval, the script
pauses. A banner appears in the app (plus a desktop notification with
Allow/Deny), and the AI is told via `waitingForApproval` in `run_code` /
`get_job`. You can allow or deny once, or always. Unanswered requests expire
after `NEXORA_APPROVAL_TIMEOUT` (default `5m`). Blocked tools are removed
from the API the AI sees. Settings live in `~/.config/nexora/permissions.json`
and are cleared when an extension is uninstalled.
